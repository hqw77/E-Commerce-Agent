# 0. 文档说明

## 0.1 文档目的

本文档定义 E-Commerce Agent V1.2 的系统总体架构。

重点明确：

1. 系统整体由哪些技术组件和业务模块组成。
2. 前端、API、Service、Repository 和数据库之间的职责边界。
3. 电商业务域与 AI 应用域之间的关系。
4. RAG 知识库的数据处理和检索流程。
5. LangGraph Agent 如何通过 Tool 调用电商业务。
6. 用户身份、权限和高风险操作如何得到控制。
7. MySQL、Redis、向量存储和 LLM API 各自承担什么职责。
8. 系统如何进行异常处理、日志记录、运行追踪和部署。

本文档定义总体架构约束，不替代各 TASK 的详细技术设计。

## 0.2 架构设计原则

本项目遵循以下原则：

| 原则           | 说明                                        |
| -------------- | ------------------------------------------- |
| 模块化单体     | 一个后端应用，内部按业务和技术职责分层      |
| 业务优先       | 先保证业务规则正确，再引入 AI 能力          |
| 职责分离       | API、Service、Repository、Database 各司其职 |
| AI 受控执行    | Agent 不能直接访问数据库                    |
| 复用业务能力   | AI Tool 必须复用已有业务 Service            |
| 数据权威性     | MySQL 是电商业务数据的唯一权威来源          |
| 知识与业务分离 | RAG 提供知识，不代替实时业务查询            |
| 权限后端执行   | 不能依赖 Prompt 保证业务权限                |
| 高风险操作确认 | 重要写操作需要确认和后端二次校验            |
| 可测试         | 核心业务和 AI 流程都应具备自动化测试        |
| 可部署         | 使用 Docker Compose 和 Nginx 完成生产部署   |
| 控制复杂度     | 不为追求架构复杂度引入不必要的基础设施      |

## 0.3 当前实现状态说明

本文档中涉及的系统能力分为：

- **已实现**：已经在当前仓库中完成开发。
- **规划中**：属于 V1.2 后续 TASK，需要继续开发。
- **待决策**：尚未确定具体技术方案，需要在对应 TASK 详细设计阶段确认。

不能将规划中的功能描述为当前已经可用的功能。

# 1. 系统总体架构

## 1.1 系统定位

E-Commerce Agent 是一个由传统电商业务系统和 AI Agent 应用组成的模块化单体应用。

传统电商业务负责：

- 用户；
- 商品；
- SKU；
- 库存；
- 订单；
- 支付；
- 售后。

AI 应用负责：

- 用户自然语言交互；
- 业务知识检索；
- 意图理解；
- 工具选择；
- 工作流编排；
- 受控业务操作；
- 结果解释；
- 运行追踪和效果评测。

AI 应用建立在现有电商业务系统之上，而不是重新实现一套电商业务。

## 1.2 总体逻辑架构

```text
                         用户

              ┌───────────┴───────────┐
              │                       │
         React 前端               用户/API 客户端
              │                       │
              └───────────┬───────────┘
                          │
                       Nginx
                          │
                    FastAPI API
                          │
          ┌───────────────┴────────────────┐
          │                                │
       业务 API                         AI API
          │                                │
    ┌─────┴─────┐                    Agent Runtime
    │           │                         │
  Service   Repository                 LangGraph
    │           │                         │
    │         MySQL                 Reasoning / Workflow
    │                                     │
    │                               Tool Registry
    │                                     │
    │                                  Tool
    │                                     │
    └─────────────────────────────────────┘
                                          │

                                          │
                                     Repository
                                          │

                          Agent 还可以调用：

                              RAG Service
                                  │
                         Document Processing
                                  │
                             Embedding
                                  │

                    Agent / RAG 可以使用：
                       LLM API
                       Redis
                       日志与 Trace
```

上图是逻辑架构，不代表所有模块已经完成开发。

## 1.3 系统分层

系统划分为以下层次：

| 层次                 | 主要职责                                          |
| -------------------- | ------------------------------------------------- |
| Presentation Layer   | 用户界面和 HTTP 请求入口                          |
| API Layer            | 路由、请求校验、身份认证、响应封装                |
| Application Layer    | 业务 Service、Agent Runtime、RAG 编排             |
| Domain Layer         | 核心业务规则和领域模型                            |
| Infrastructure Layer | 数据库、Redis、LLM、Embedding、向量存储等技术设施 |
| Data Layer           | 业务数据和知识索引的持久化                        |

不同层次之间通过明确的接口协作。

不允许因为某个模块需要方便，就跳过中间层直接访问其他模块的内部实现。

# 2. 总体架构模式

## 2.1 模块化单体

第一版采用模块化单体（Modular Monolith）。

特点：

1. 后端以一个 FastAPI 应用运行。
2. 不拆分成多个独立微服务。
3. 各业务模块有明确的代码边界。
4. 业务规则集中在对应 Service。
5. 数据访问通过 Repository。
6. AI Agent 作为后端应用内部的独立能力模块。
7. 外部模型服务通过 API 调用。

逻辑上的模块分离不等于物理上的服务拆分。

## 2.2 为什么选择模块化单体

本项目主要目标是构建一个完整、可运行、可维护的工程实践作品。

模块化单体具有以下优势：

- 开发和调试成本较低；
- 业务调用链容易理解；
- 事务处理更加直接；
- 部署成本较低；
- 不需要引入复杂服务通信；
- 方便学习和展示完整业务流程；
- 为未来模块独立演进保留空间。

第一版不引入微服务、Kubernetes、服务网格和复杂分布式事务。

## 2.3 模块边界

系统逻辑上分为：

```text

│
├── Business Domain
│   ├── User
│   ├── Product
│   ├── Category
│   ├── SKU
│   ├── Inventory
│   ├── Order
│   ├── Payment
│   └── After-Sales
│
├── AI Application Domain
│   ├── Agent
```

# 3. 后端分层架构

## 3.1 API Layer

API Layer 是系统对外提供 HTTP 服务的入口。

主要职责：

- 接收 HTTP 请求；
- 解析请求参数；
- 使用 Pydantic 校验请求数据；
- 处理身份认证；
- 执行必要的接口级权限检查；
- 调用对应 Service；
- 返回统一响应；
- 处理 API 层异常。

API 层不应包含复杂业务规则。

例如：

创建订单 API 的主要职责是：

1. 接收商品 SKU 和购买数量；
2. 校验请求格式；
3. 获取当前登录用户；
4. 调用订单 Service；
5. 返回创建结果。

订单金额计算、库存预占、订单状态变更等规则必须由 Service 实现。

## 3.2 Application Service Layer

Service Layer 是业务应用的核心。

主要职责：

- 实现业务用例；
- 组织多个 Repository；
- 执行业务规则；
- 管理数据库事务；
- 进行资源归属检查；
- 处理业务状态变化；
- 保证关键业务操作的幂等性；
- 统一处理业务异常。

例如订单 Service：

```text
OrderService
    │
    ├── 校验用户身份
    ├── 校验商品和 SKU
    ├── 校验库存
    ├── 计算订单金额
    ├── 创建订单
    ├── 保存订单快照
    ├── 预占库存
    └── 提交事务
```

上述是职责示意，具体事务、锁和状态规则以 TASK-004.1 设计为准。

Service 是普通业务 API 和 Agent Tool 共同使用的业务入口。

不允许 Agent Tool 自己再实现一套订单业务规则。

## 3.3 Domain Layer

Domain Layer 表达核心业务概念和业务规则。

例如：

- User；
- Product；
- SKU；
- Inventory；
- Order；
- Payment；
- AfterSales；
- Refund。

Domain Layer 不应该依赖具体的 HTTP 请求对象或大语言模型消息对象。

业务状态、金额计算和资源约束应由业务模型及对应 Service 管理。

## 3.4 Repository Layer

Repository Layer 负责数据访问。

主要职责：

- 查询数据；
- 新增数据；
- 更新数据；
- 删除数据；
- 管理数据库查询；
- 配合 Service 完成事务中的数据操作。

Repository 不负责决定完整业务流程。

例如：

`OrderRepository` 可以查询订单、更新订单状态、获取订单明细，但是否允许取消订单必须由 Order Service 判断。

## 3.5 Database Layer

Database Layer 负责数据库连接、Session、ORM 模型和数据库事务基础设施。

主要包括：

- SQLAlchemy Async；
- AsyncSession；
- ORM Models；
- 数据库连接池；
- Alembic；
- Migration。

业务主数据使用 MySQL 8。

数据库结构变化通过 Alembic 迁移管理，不允许只修改 ORM 模型而忽略数据库迁移。

# 4. 业务域与 AI 域边界

## 4.1 业务域

业务域负责系统中具有确定性规则的业务操作。

主要包括：

| 模块        | 职责               |
| ----------- | ------------------ |
| User        | 用户身份和用户数据 |
| Product     | 商品管理           |
| Category    | 商品分类           |
| SKU         | 商品销售规格       |
| Inventory   | 库存与库存流水     |
| Order       | 订单创建和状态管理 |
| Payment     | 支付单与支付状态   |
| After-Sales | 售后申请与处理     |
| Refund      | 退款记录与退款流程 |

业务域必须保证：

- 数据一致性；
- 状态转换合法；
- 资源归属正确；
- 金额计算正确；
- 幂等；
- 并发安全；
- 权限检查有效。

这些规则不能依赖大语言模型判断。

## 4.2 AI 应用域

AI 应用域负责自然语言理解、知识检索和工具编排。

主要包括：

| 模块          | 职责                        |
| ------------- | --------------------------- |
| Interaction   | 接收用户消息并返回结果      |
| Reasoning     | 理解意图并选择下一步        |
| Knowledge     | 获取业务知识                |
| Tools         | 将业务能力包装为 Agent 工具 |
| Workflow      | 管理 Agent 执行流程         |
| Guardrails    | 权限和安全约束              |
| Verification  | 检查工具结果和执行结果      |
| Observability | 运行日志和 Trace            |
| Evaluation    | 评估 Agent 效果             |
| Performance   | 管理延迟和成本              |

AI 应用域不负责重新定义电商业务规则。

## 4.3 两个领域的关系

```text
                   用户请求
                      │
                      ▼
                 Agent Runtime
                      │
             ┌────────┴────────┐
             │                 │
          RAG 检索           Tool Calling
             │                 │
             ▼                 ▼
         RAG Service        Business Tool
             │                 │
             ▼                 ▼
         Vector Store       Business Service
                               │
                               ▼
                           Repository
                               │
                               ▼
                             MySQL
```

RAG 负责提供文档知识。

Business Service 负责真实业务数据和业务操作。

两者不能相互替代。

# 5. 核心基础设施组件职责

## 5.1 MySQL

MySQL 是系统业务数据的权威数据源。

保存：

- 用户；
- 商品；
- 分类；
- SKU；
- 库存；
- 库存流水；
- 订单；
- 订单明细；
- 支付单；
- 售后申请；
- 退款记录；
- 知识库文档元数据；
- 必要的 Agent 业务执行记录。

业务数据的最终正确性以 MySQL 中的业务记录和事务结果为准。

不能把向量数据库中的文本内容当作实时库存、订单状态或支付状态的权威来源。

## 5.2 Redis

Redis 用于需要快速访问的短期数据和辅助并发控制。

规划用途包括：

- 缓存；
- 短期会话状态；
- Agent 临时运行状态；
- 操作确认 nonce；
- 限流辅助；
- 并发控制辅助；
- 短期任务状态。

Redis 不能无条件代替 MySQL 保存关键业务事实。

涉及高风险操作时，Redis 原子操作、数据库事务和业务幂等机制需要根据具体场景组合使用。

Redis 的具体键结构、过期策略和持久化策略由相应 TASK 详细设计确定。

## 5.3 Vector Store

Vector Store 用于保存文档切分后的向量表示和检索所需数据。

主要用途：

- 语义检索；
- 相关文档片段召回；
- RAG 上下文构建；
- 文档来源定位。

Vector Store 不负责：

- 商品实时库存；
- 订单状态；
- 支付状态；
- 退款状态；
- 用户权限的最终判断。

具体向量数据库产品尚未冻结，在 TASK-005 详细设计中确定。

## 5.4 LLM API

LLM API 用于：

- 自然语言理解；
- 意图识别；
- 对话生成；
- 工具选择；
- 参数生成；
- 检索内容总结；
- Agent 推理。

LLM 输出是不可信的外部计算结果。

必须通过后端逻辑校验参数、权限和业务状态。

模型 API Key 由后端配置和密钥管理机制保护，不能发送给浏览器或写入普通日志。

## 5.5 Embedding API

Embedding API 用于将文本转换为向量。

主要用于：

- 文档入库；
- 查询向量生成；
- 语义检索。

文档向量和查询向量必须使用兼容的模型与维度配置。

模型变更可能影响已有向量索引，需要在 TASK-005 设计中明确版本管理和重建策略。

## 5.6 外部支付服务

支付宝作为外部支付服务。

后端负责：

- 生成支付请求；
- 使用安全配置的密钥签名；
- 接收支付通知；
- 验证通知签名；
- 查询支付结果；
- 关闭支付；
- 发起退款；
- 查询退款结果。

浏览器和 Agent 都不能直接持有支付宝私钥。

支付业务规则以 TASK-004.1 设计和对应支付实现为准。

# 6. Agent 与业务系统交互架构

## 6.1 强制调用链

所有 Agent 业务操作必须遵循：

```text
Agent
  ↓
Tool
  ↓
Service
  ↓
Repository
  ↓
Database
```

每一层的职责：

| 层次       | 职责                                   |
| ---------- | -------------------------------------- |
| Agent      | 根据用户意图决定是否需要工具           |
| Tool       | 定义工具名称、描述、参数和调用入口     |
| Service    | 校验权限、业务规则、资源状态并执行用例 |
| Repository | 负责数据库读写                         |
| Database   | 持久化业务数据                         |

## 6.2 Tool 的职责

Tool 是 Agent 与业务系统之间的受控适配层。

Tool 负责：

- 向模型提供清晰的工具描述；
- 定义严格的输入 Schema；
- 校验工具参数格式；
- 获取后端提供的用户身份上下文；
- 调用对应 Service；
- 将 Service 结果转换成适合 Agent 理解的结构；
- 处理可预期的业务错误。

Tool 不负责：

- 自行计算订单金额；
- 自行修改库存；
- 自行判断是否允许退款；
- 自行绕过用户权限；
- 直接执行 SQL；
- 直接访问 Repository；
- 自己实现订单状态转换。

## 6.3 用户身份传递

用户身份必须由后端认证系统提供。

正确方式：

```text
HTTP Request
    │
    ▼
JWT Authentication
    │
    ▼
Current User Context
    │
    ▼
Agent Runtime
    │
    ▼
Tool Execution Context
    │
    ▼
Business Service
```

Agent 不得通过模型生成的参数决定用户身份。

例如：

模型即使生成：

```json
{
  "user_id": 100,
  "is_admin": true
}
```

也不能因此获得用户 100 或管理员权限。

Service 必须根据可信的后端身份上下文执行权限检查。

## 6.4 业务工具权限

每个 Tool 都应定义：

- 工具用途；
- 参数 Schema；
- 允许调用的用户类型；
- 所需权限；
- 对应 Service；
- 是否只读；
- 是否有业务副作用；
- 是否需要确认；
- 幂等要求；
- 审计要求。

工具白名单由后端管理。

模型不能自行创建新工具或调用未注册的工具。

## 6.5 工具执行结果

Tool 返回结构化结果。

示意：

```json
{
  "success": true,
  "code": "ORDER_FOUND",
  "message": "订单查询成功",
  "data": {
    "order_no": "示例订单号",
    "status": "PAID"
  }
}
```

以上仅为结构示意，实际字段和错误码由 TASK-007 详细设计确定。

Agent 可以解释工具结果，但不能篡改业务执行结果。

# 7. RAG 知识库架构

## 7.1 RAG 定位

RAG 为 Agent 提供业务文档知识。

适合回答：

- 商品使用说明；
- 售后规则；
- 退换货政策；
- 配送政策；
- 常见问题；
- 业务操作说明。

不适合回答需要实时查询业务数据库的问题。

例如：

| 用户问题           | 正确处理方式                      |
| ------------------ | --------------------------------- |
| 商品支持哪些功能？ | RAG                               |
| 退货政策是什么？   | RAG                               |
| 我的订单到哪里了？ | 订单 Tool                         |
| 商品还剩多少库存？ | 库存 Tool                         |
| 我的退款是否到账？ | 退款 Tool                         |
| 如何申请售后？     | RAG 解释规则，必要时调用售后 Tool |

## 7.2 文档入库流程

```text
管理员上传文档
       │
       ▼
Knowledge API
       │
       ▼

       ▼
Document Storage
       │

Document Parser
       │

Text Extraction

Text Chunking
       │
       ▼
Embedding API
       │
       ▼
Vector Store
       │
       ▼

```

文档元数据和生命周期由业务数据库管理。

向量存储负责保存检索数据。

文件原件的存储方式和具体组件由 TASK-005 设计确定。

## 7.3 文档检索流程

```text
用户问题
   │
```

具体检索方式可能包括向量检索、关键词检索和混合检索。

Reranker 属于 TASK-005 的技术评估范围。第一版不强制引入，根据检索质量评测结果决定是否采用，最终方案在 TASK-005 详细设计中冻结。

## 7.4 RAG 安全边界

RAG 文档内容属于不可信外部数据。

文档中即使包含：

- 忽略系统提示词；
- 修改 Agent 权限；
- 输出系统密钥；
- 调用未授权工具；
- 执行任意 SQL；

也不能覆盖系统指令或后端权限。

必须遵守：

1. 文档内容不能成为系统级指令。
2. 文档不能授予用户权限。
3. 检索结果不能绕过 Service。
4. 检索必须执行文档可见性权限过滤。
5. 文档更新或删除后，旧版本不能继续被检索。
6. 答案应尽可能提供可追溯的来源引用。

具体安全策略见 `docs/architecture.md`，详细实现由 TASK-005 确定。

# 8. 用户认证与权限架构

## 8.1 认证流程

```text
用户登录
   │
   ▼
FastAPI Authentication API
   │
   ▼
User Service
   │
   ▼
验证密码
   │
   ▼
签发 Access Token
   │
   ▼
签发 Refresh Token
   │
   ▼
客户端保存 Token
```

后续请求通过 Access Token 识别当前用户。

Refresh Token 用于安全刷新访问凭据。

当前认证模块已经具备用户认证和 Refresh Session 基础能力。

## 8.2 API 权限控制

API 请求需要经过：

1. Token 验证；
2. 当前用户解析；
3. 接口级权限检查；
4. Service 业务权限检查；
5. 资源归属检查。

不能只依赖前端隐藏按钮来控制权限。

## 8.3 AI Agent 权限控制

Agent 的权限不能高于当前用户实际拥有的权限。

Agent 调用 Tool 时：

- 用户身份由后端提供；
- 工具参数由 Schema 校验；
- Service 再次检查权限；
- Service 检查资源归属；
- Service 检查业务状态；
- 必要时要求用户确认。

## 8.4 当前版本权限范围

V1.2 不建设多租户权限体系。

第一版只实现项目实际需要的：

- 用户身份；
- 基础管理员权限；
- 用户资源归属；
- 必要的文档可见性控制；
- 业务操作权限。

不将 `tenant_id` 设计为当前版本强制字段。

# 9. 高风险业务操作架构

## 9.1 操作分类

Agent 操作分为：

| 类型         | 示例                           | 处理方式             |
| ------------ | ------------------------------ | -------------------- |
| 只读         | 商品查询、库存查询、订单查询   | 权限校验后执行       |
| 普通写操作   | 允许范围内的低风险数据修改     | Service 校验后执行   |
| 高风险写操作 | 订单取消、退款、售后状态变更等 | 根据业务风险要求确认 |

具体哪些工具必须确认，由 TASK-007 详细设计确定。

## 9.2 Prepare / Confirm 流程

高风险操作不能仅凭模型生成一次 Tool Call 就直接执行。

基本流程：

```text
用户提出操作请求
       │
       ▼
Agent 识别操作意图
       │
       ▼
Prepare Tool
       │
       ▼
后端验证用户与业务状态
       │
       ▼
生成待确认操作凭据
       │
       ▼
向用户展示操作摘要
       │
       ▼
用户明确确认
       │
       ▼
Confirm Tool
       │
       ▼
验证确认凭据
       │
       ▼
重新校验权限和业务状态
       │
       ▼
执行 Service
       │
       ▼
记录审计结果
```

## 9.3 确认凭据要求

确认凭据至少需要绑定：

- 用户；
- 会话；
- 操作类型；
- 目标资源；
- 关键操作参数；
- 参数摘要或哈希；
- 随机 nonce；
- 过期时间；
- 消费状态。

如果操作参数发生变化，必须重新确认。

## 9.4 并发与防重放

一次性确认不能只依赖应用层先查询、再修改。

必须使用具备原子性的消费机制，例如：

- Redis 原子操作；
- 数据库事务与条件更新。

具体实现根据确认凭据存储方式确定。

此外，还必须结合业务幂等机制。

确认凭据的一次性消费不能替代订单、退款等业务自身的幂等保护。

## 9.5 最终安全边界

即使：

- 用户已经确认；
- Agent 判断操作合理；
- Tool 参数合法；
- 确认凭据有效；

Service 仍然必须重新验证业务状态、用户权限和资源归属。

Service 是最终业务安全边界。

# 10. 同步与异步处理架构

## 10.1 第一版基本原则

第一版以同步 HTTP API 和应用内部异步调用为主。

后端使用 FastAPI 和 SQLAlchemy Async。

涉及外部 API 的调用必须合理控制超时。

## 10.2 适合同步执行的操作

- 库存查询；
- 订单查询；
- 订单创建；

# 11. 异常处理、日志与可观测性

## 11.1 异常处理

系统异常需要区分：

- 参数校验异常；
- 身份认证异常；
- 权限异常；
- 业务规则异常；
- 数据库异常；
- 外部服务异常；
- LLM 调用异常；
- RAG 检索异常；
- Tool 执行异常；
- 工作流异常。

异常处理应当：

1. 使用明确的错误类型；
2. 保留内部诊断信息；
3. 向客户端返回安全、可理解的错误信息；
4. 不暴露数据库结构和敏感凭据；
5. 对可恢复异常实施合理重试；
6. 避免对非幂等操作进行无条件重试。

## 11.2 日志

日志用于记录系统运行过程和排查问题。

至少需要关注：

- 请求 ID；
- 用户身份标识；
- API 路由；
- 业务操作；
- 业务结果；
- 错误类型；
- 外部服务调用结果；
- Agent 执行结果；
- Tool 调用记录。

日志中不得记录：

- 明文密码；
- API Key；
- 支付私钥；
- 完整敏感 Token；
- 不必要的个人敏感信息。

## 11.3 Agent Trace

规划记录：

- 会话标识；
- Agent 运行标识；
- 用户请求；
- 模型调用；
- Prompt 版本；
- 工具选择；
- 工具参数摘要；
- Tool 执行结果；
- RAG 检索结果标识；
- 执行耗时；
- Token 使用量；
- 异常信息。

Trace 必须执行敏感信息脱敏。

不能因为调试方便而完整记录密钥、支付凭据或敏感个人数据。

## 11.4 可观测性目标

系统需要能够回答：

- 一次 Agent 请求经历了哪些步骤？
- 调用了哪个模型？
- 检索到了哪些文档？
- 选择了哪个 Tool？
- Tool 是否执行成功？
- 失败发生在哪一层？
- 请求消耗了多少时间？
- 模型调用产生了多少成本？

具体日志结构、Trace 存储和指标方案由 TASK-006、TASK-015 进一步确定。

# 12. 安全架构

## 12.1 安全设计原则

AI 系统中的以下内容都不能默认可信：

- 用户输入；
- RAG 文档；
- 模型输出；
- Tool 输出；
- 外部 API 返回内容。

可信的安全控制来自后端认证、权限校验、业务 Service 和基础设施。

## 12.2 Prompt Injection

需要考虑：

- 直接 Prompt Injection；
- 间接 Prompt Injection；
- 文档中的恶意指令；
- 中文、英文及混合语言诱导；
- 编码和混淆内容；
- 多轮对话诱导；
- 伪造系统消息；
- 伪造工具执行结果。

不能只依赖 System Prompt 或关键词黑名单。

## 12.3 Tool 安全

必须实施：

- 工具白名单；
- 严格参数 Schema；
- 后端身份上下文；
- Service 权限校验；
- 资源归属校验；
- 业务状态校验；
- 高风险操作确认；
- 幂等；
- 审计。

禁止提供任意 SQL、Shell、文件系统或无限制 HTTP 请求工具。

## 12.4 凭据保护

以下内容必须受到保护：

- LLM API Key；
- Embedding API Key；
- 数据库密码；
- Redis 密码；
- JWT Secret；
- 支付宝私钥；
- 支付宝应用密钥等敏感凭据。

密钥不能进入：

- 前端代码；
- Git 仓库；
- 普通应用日志；
- Agent Prompt；
- 模型请求内容；
- 未经脱敏的 Trace。

## 12.5 安全基线引用

安全设计详细内容以 `docs/architecture.md` 为准。

该文件当前的 Review 和冻结状态以项目实际记录为准。

本文档只明确系统总体安全边界，不代表安全基线已经正式通过 Review。

生产环境必须：

- 使用独立生产配置；
- 使用环境变量或受控密钥配置；

- 限制数据库对公网暴露；
- 限制 Redis 对公网暴露；

- 定期备份关键数据。

# 15. 架构约束与明确不做的内容

## 15.1 必须遵守的架构约束

1. 使用模块化单体。
2. 业务逻辑集中在 Service。
3. 数据访问集中在 Repository。
4. Agent 必须通过 Tool 调用 Service。
5. Agent 不允许直接访问数据库。
6. Tool 不允许绕过 Service。
7. RAG 不替代实时业务查询。
8. MySQL 是业务数据的权威来源。
9. 用户权限由后端认证和业务逻辑执行。
10. 高风险操作需要后端确认和二次校验。
11. 关键操作必须具备幂等和并发保护。
12. 敏感凭据不得暴露给模型、前端和日志。
13. 文档内容和模型输出不能成为权限来源。
14. 系统必须保留必要的审计和运行记录。

## 15.2 明确不做

第一版不引入：

- 微服务；
- Kubernetes；
- 服务网格；
- 自研消息队列；
- 多租户体系；
- 复杂分布式事务平台；
- 任意 SQL Agent；
- 任意 Shell Agent；
- 无限制自主执行；
- 完整企业级权限中心。

不为了架构图复杂而增加实际项目不需要的组件。

# 18. 架构变更原则

以下内容属于 V1.2 架构基线：

- 模块化单体；
- 业务域和 AI 应用域分离；
- Agent → Tool → Service → Repository → Database；
- MySQL 作为业务数据权威来源；
- RAG 与实时业务查询分离；
- 后端执行身份和权限校验；
- 高风险操作采用受控确认；
- 不引入微服务、Kubernetes 和多租户。

如果后续需要调整这些基线，应说明：

1. 当前方案存在什么问题；
2. 影响哪些业务模块；
3. 对现有代码和数据库的影响；
4. 是否影响已完成 TASK；
5. 是否需要数据迁移；
6. 新方案带来的成本和收益。

经项目负责人确认后才能修改架构基线。
