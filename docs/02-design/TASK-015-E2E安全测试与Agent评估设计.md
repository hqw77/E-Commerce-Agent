## 1. 任务概述

### 1.1 任务背景

TASK-014 完成后，前后端已经实现真实业务联调。

但接口能正常返回，并不代表系统已经具备可靠性和安全性。

本任务需要进一步验证：

- 用户能否通过完整业务流程完成操作；
- 数据库事务和状态机是否正确；
- 多用户之间是否存在数据越权；
- Agent 是否可能被诱导绕过 Tool 权限；
- Prepare / Confirm 是否能抵抗重放和并发；
- 支付回调是否满足幂等性；
- RAG 检索是否有实际效果；
- Agent 的回答和 Tool 调用是否符合预期。

### 1.2 核心目标

1. 建立核心业务端到端测试。
2. 验证认证、授权、数据隔离和业务安全。
3. 验证支付沙箱与回调处理。
4. 验证 Agent Tool 和 Prepare / Confirm 安全边界。
5. 建立 RAG 检索效果评估集。
6. 建立 Agent 回答与 Tool 调用评估集。
7. 输出可重复执行的测试报告。

### 1.3 非目标

本任务不负责：

- 引入独立安全平台；
- 引入复杂 Agent 评测平台；
- 自建模型；
- 大规模压力测试平台；
- 自动化渗透测试平台；
- 修改已经冻结的业务规则；
- 重新实现 Agent 或 RAG；
- 生产云服务器部署。

## 3. 测试环境与数据管理

### 3.1 环境要求

- Python 3.12。
- FastAPI。
- MySQL 8。
- Redis。
- Qdrant。
- BGE-M3 Embedding。
- DeepSeek API。
- pytest。
- 前端 Vitest 和现有浏览器自动化能力。

测试使用独立测试环境，不能直接对真实业务数据执行写操作。

### 3.2 测试数据

建立可重复初始化的测试数据：

| 数据         | 用途           |
| ------------ | -------------- |
| 普通用户 A   | 正常用户流程   |
| 普通用户 B   | 用户隔离测试   |
| 管理员       | 管理权限测试   |
| 测试商品     | 商品和订单流程 |
| 测试 SKU     | 库存和订单流程 |

| 测试支付记录 | 支付回调       |

数据要求：

- 测试数据必须有明确标识。

### 3.3 外部依赖处理

分为两种模式：

**自动化模式**

使用 Fake LLM、Mock 支付客户端和测试数据库，保证测试可重复执行。

**真实集成模式**

使用真实 DeepSeek API、BGE-M3、Qdrant 和支付宝沙箱，验证外部服务集成。

两种模式都需要保留，不能只依赖 Mock 测试。

## 4. Backend 端到端测试

### 4.1 认证流程

测试链路：

```text
注册
  ↓
登录
  ↓
获取当前用户
  ↓
访问受保护 API
  ↓
刷新 Token
  ↓
使用新 Token
  ↓
登出
  ↓
旧 Refresh Session 失效
```

测试场景：

- 正常注册和登录。
- 重复邮箱注册。
- 错误密码。
- 无效 Access Token。
- Access Token 过期。
- Refresh Token 正常轮换。
- Refresh Token 重放。
- 用户登出。
- 已撤销 Refresh Session 再次使用。

### 4.2 商品与库存流程

测试链路：

```text
管理员创建分类
    ↓
创建商品
    ↓
创建 SKU
    ↓
初始化库存
    ↓
库存入库
    ↓
查询库存
    ↓
查询库存流水
```

测试重点：

- SKU 与商品关联正确。
- 库存数量变化正确。
- 库存流水正确。
- 并发库存修改符合现有事务和锁规则。
- 非法库存调整被拒绝。
- 普通用户无法执行管理员操作。

### 4.3 订单流程

测试链路：

```text
创建订单
   ↓
锁定库存
   ↓
创建支付记录
   ↓
订单状态更新
   ↓
支付成功
   ↓
订单状态更新
   ↓
库存扣减确认
```

同时测试：

- 重复创建订单。
- 订单幂等性。
- 库存不足。
- 并发订单。
- 支付超时。
- 支付失败。
- 重复支付回调。
- 非法状态转换。
- 用户只能访问自己的订单。

具体状态转换以 TASK-004 已冻结的订单和支付设计为准，不重新定义状态机。

### 4.4 取消订单

测试：

- 允许取消的订单。
- 不允许取消的订单。
- 库存释放。
- 库存流水。
- 支付记录关闭。
- 重复取消。
- 并发取消。

最终验证数据库中订单、库存和流水的一致性。

### 4.5 售后流程

测试：

- 符合条件的售后申请。
- 不符合条件的售后申请。
- 重复申请。
- 非订单所有者申请。
- 非法售后状态操作。
- 售后申请和订单状态关系。
- 退款流程中的幂等处理。

不在本任务中自行扩大现有售后业务规则。

## 5. 支付沙箱与回调测试

### 5.1 测试目标

TASK-004 已完成支付业务代码和自动化测试，但支付宝真实沙箱 E2E、通知及退款查询仍需验证。

本任务补齐真实支付沙箱集成验证。

### 5.2 测试流程

```text
创建订单
   ↓
创建支付单
   ↓
调用支付宝沙箱
   ↓
获取支付信息
   ↓
模拟或完成沙箱支付
   ↓
接收异步通知
   ↓
验证签名
   ↓
验证金额和商户订单信息
   ↓
更新支付状态
   ↓
更新订单状态
```

### 5.3 必须测试的场景

1. 正常支付。
2. 支付成功通知。
3. 重复通知。
4. 无效签名。
5. 金额不一致。
6. 商户订单号不匹配。
7. 未知支付单。
8. 已关闭支付单收到迟到通知。
9. 通知处理异常后的重试。
10. 主动查询支付结果。

### 5.4 幂等性验证

同一笔成功通知重复提交：

- 不得重复扣减库存。
- 不得重复更新订单状态。
- 不得产生重复业务副作用。
- 应按现有实现返回支付平台认可的通知响应。

### 5.5 退款验证

在支付宝沙箱支持的范围内验证：

- 退款请求。
- 退款结果查询。
- 重复退款请求。
- 退款结果与本地状态一致性。

沙箱不支持的真实能力必须如实记录，不能用 Mock 结果宣称真实支付验证通过。

### 5.6 密钥管理

- 使用独立沙箱密钥。
- 密钥通过环境变量注入。
- 不提交私钥。
- 不打印完整签名和敏感请求内容。
- 不使用生产支付密钥。
- 不在报告中展示真实凭据。

## 6. 安全测试

### 6.1 认证安全

验证：

- 无 Token 访问受保护 API。
- 伪造 JWT。
- 错误签名。
- Token 过期。
- Refresh Token 重放。
- 已撤销会话。
- 并发刷新。
- 不同用户 Token 混用。

### 6.2 授权与数据隔离

建立用户 A、用户 B 和管理员三个身份。

验证：

| 场景                                | 预期                         |
| ----------------------------------- | ---------------------------- |
| A 访问自己的订单                    | 允许                         |
| A 访问 B 的订单                     | 拒绝或按既有资源隐藏策略返回 |
| B 访问 A 的售后                     | 拒绝                         |
| 普通用户调用管理员 API              | 403                          |
| 普通用户读取 ADMIN_ONLY 文档        | 无法获取                     |
| 普通用户通过 Agent 查询其他用户订单 | 无法获取                     |

权限必须由 Backend Service / API 和 RAG ACL 保证，不能依赖前端隐藏按钮。

### 6.3 Agent 安全

重点验证 Agent 不能因为用户指令而突破后端权限。

测试内容：

- Prompt Injection。
- 要求泄露 System Prompt。
- 要求输出 API Key、JWT 和内部配置。
- 伪造管理员身份。
- 指定其他用户 ID 查询订单。
- 绕过 Tool Registry 调用未注册工具。
- 伪造 Tool 参数。
- 请求执行未开放业务操作。
- 使用 RAG 文档中的恶意指令诱导 Agent。
- 用户 A 的会话访问用户 B 的数据。

必须遵守：

```text
模型输出 ≠ 用户权限
Prompt ≠ 安全边界
Tool Allow-list ≠ 完整授权
Service 权限校验 = 最终业务边界
```

任何业务写操作必须经过现有 Prepare / Confirm 和 Service 规则。

### 6.4 Prepare / Confirm 安全

重点测试：

1. 正常 Prepare。
2. 正常 Confirm。
3. 错误 nonce。
4. 错误 conversation_id。
5. 其他用户使用确认凭证。
6. 凭证过期。
7. 凭证重复消费。
8. 并发 Confirm。
9. 修改业务参数。
10. 修改订单资源。
11. Redis 确认记录不存在。
12. Confirm 业务执行失败。

验收要求：

- 同一确认凭证只能成功消费一次。
- 并发确认最多一个请求成功执行。
- 用户、会话、动作、资源和参数绑定有效。
- 前端不能覆盖 Prepare 中的业务参数。
- 失败场景不能产生重复业务副作用。

### 6.5 Web 安全

检查：

- XSS 风险。
- 用户输入渲染。
- 文件上传类型和大小限制。
- 敏感信息泄露。
- 日志脱敏。
- 错误堆栈暴露。
- JWT 和 Refresh Token 暴露。
- CORS 和反向代理边界。
- 环境变量和密钥管理。

当前前端使用 localStorage 保存 Token 的风险必须在报告中明确记录。

本任务先评估并验证风险，不允许未经设计就随意更换认证架构。

## 7. RAG 效果评估

### 7.1 评估目标

不仅验证 RAG API 能返回结果，还需要证明检索结果具有实际相关性。

### 7.2 评估数据集

建立独立评估数据集，建议第一版至少包含 25 个问题，覆盖：

- 商品知识。
- 订单规则。
- 支付规则。
- 退款规则。
- 售后规则。

每条数据至少包含：

```json
{
  "query": "用户问题",
  "expected_document_ids": ["doc-001"],
  "expected_chunk_ids": ["chunk-001"]
}
```

具体 ID 以真实测试知识库为准。

数据集应包含：

- 明确答案问题。
- 同义表达问题。
- 多文档问题。
- 不相关问题。
- 知识库中不存在答案的问题。

### 7.3 指标

至少计算：

**Recall@K**

检索结果中是否找到了预期相关文档。

**Precision@K**

前 K 条检索结果中相关结果占比。

**MRR**

第一个相关结果的倒数排名。

**Empty Retrieval Rate**

检索没有返回任何结果的比例。

**No-answer Accuracy**

知识库没有答案时，系统是否能够正确表示不知道。

已有 TASK-005 的评估指标和脚本继续复用，不重新实现另一套评估系统。

### 7.4 评估要求

- 记录评估数据集版本。
- 记录 Embedding 模型。
- 记录向量库配置。
- 记录 Top-K 和阈值。
- 保存评估结果。
- 对比现有基线。
- 不通过删除困难问题来提高指标。

现有 TASK-005 评估结果 Recall@5 = 1.0、MRR = 1.0、Precision@5 = 0.2、Empty Retrieval Rate = 0.0，可作为历史基线，但不能直接视为新评估集的结果。

## 8. Agent 效果评估

### 8.1 评估范围

Agent 评估分为三部分：

1. 普通对话。
2. RAG 知识问答。
3. 业务 Tool 调用。

### 8.2 测试集

第一版建议至少 30 个用例。

覆盖：

- 普通闲聊。
- 商品搜索。
- 商品详情。
- SKU 查询。
- 库存查询。
- 订单列表。
- 订单详情。
- 售后查询。
- 取消订单 Prepare。
- 售后申请 Prepare。
- 未授权操作。
- 不完整参数。
- 非法参数。
- Prompt Injection。
- 不存在的数据。

### 8.3 评估指标

| 指标                        | 含义                     |
| --------------------------- | ------------------------ |
| Intent Accuracy             | 意图识别正确率           |
| Tool Selection Accuracy     | Tool 选择正确率          |
| Argument Accuracy           | Tool 参数正确率          |
| Tool Execution Success Rate | Tool 执行成功率          |
| Grounded Answer Rate        | 回答有真实数据依据的比例 |
| Unsupported Claim Rate      | 无依据陈述比例           |
| Refusal Accuracy            | 应拒绝时是否正确拒绝     |
| Citation Accuracy           | RAG 来源引用准确率       |

指标应基于测试集实际结果计算，不允许主观宣称达到某个百分比。

### 8.4 DeepSeek 真实评估

真实模型测试需要记录：

- 模型名称。
- Prompt 版本。
- 请求时间。
- Token 使用量（如果接口提供）。
- 请求耗时。
- Tool 选择。
- 最终结果。
- 失败原因。

不得将真实 API Key 写入测试数据和报告。

### 8.5 评估原则

LLM 输出存在一定随机性。

因此：

- 自动化断言优先验证结构、权限、Tool 和业务结果。
- 自然语言回答采用规则或人工抽样评估。
- 不依赖回答逐字匹配。
- 对关键安全用例要求稳定通过。
- 对非关键自然语言质量记录结果，不虚构准确率。

## 12. 风险与限制

1. DeepSeek API 的可用性和响应会影响真实 Agent 评估。
2. 支付沙箱行为不完全等于生产环境。
3. 小规模 RAG 数据集不能代表所有业务知识。
4. Prompt Injection 检测无法保证拦截所有攻击。
5. LLM 自然语言回答具有非确定性。
