# 0. 文档说明

## 0.1 设计目的

本文档定义 E-Commerce Agent 的整体能力结构、模块职责和模块之间的协作关系。

主要回答以下问题：

1. Agent 如何接收和理解用户请求？
2. Agent 如何决定直接回答、检索知识或调用业务工具？
3. Agent 如何管理对话上下文和工作流状态？
4. Agent 如何通过 Tool 调用电商业务？
5. Agent 如何执行权限校验和高风险操作确认？
6. Agent 如何验证工具执行结果？
7. Agent 如何记录运行过程并进行效果评测？
8. Agent 如何控制运行时间、模型调用次数和成本？

本文档定义 Agent 的总体设计，不替代 TASK-005、TASK-006、TASK-007 和 TASK-015 的详细设计。

## 0.2 与其他文档的关系

| 文档                             | 职责                                           |
| -------------------------------- | ---------------------------------------------- |
| `V1.2-项目总体规划.md`           | 定义项目目标、范围和开发路线                   |
| `系统总体架构.md`                | 定义系统整体架构和业务域、AI 域边界            |
| `docs/product-design.md`         | 定义商品与库存业务规则，并描述未来 AI 扩展方向 |
| `TASK-004.1-订单支付售后设计.md` | 定义订单、支付和售后业务规则                   |
| `docs/architecture.md`           | 定义 AI Agent 安全设计增补和安全基线           |

本文档不重复定义电商业务规则。

Agent 需要调用业务能力时，必须复用现有业务 Service。

## 0.3 第一版设计原则

1. Agent 是业务系统的智能交互入口，不是业务规则的最终执行者。
2. 模型负责理解、推理和生成，不负责最终权限判断。
3. Tool 是 Agent 与后端业务之间的受控接口。
4. Service 是业务规则和业务权限的最终执行边界。
5. RAG 提供知识，不代替实时业务查询。
6. 高风险操作必须经过后端确认和二次校验。
7. 所有工具必须经过后端注册和权限控制。
8. Agent 的运行过程必须可追踪、可测试、可评估。
9. 不追求无限自主执行，优先保证安全、正确和可控。
10. 第一版采用单 Agent 工作流，不建设复杂多 Agent 协作平台。

- Tools & Execution 执行受控工具调用。

- Guardrails 贯穿整个执行流程。
- Verification 检查关键结果。
- Observability 记录整个运行过程。
- Agent Evaluation 在测试和运行评估中使用。
- Performance & Cost Management 对运行过程实施资源约束。

# 2. Interaction Layer：交互层

## 2.1 模块定位

Interaction Layer 是用户与 Agent 之间的交互入口。

负责接收用户消息，将请求传递给 Agent Runtime，并将最终回答返回给用户。

它不负责实现复杂推理，也不直接执行电商业务。

## 2.2 核心职责

1. 接收用户输入。
2. 获取当前登录用户身份。
3. 获取会话标识。
4. 校验请求格式。
5. 将消息提交给 Agent Runtime。
6. 接收 Agent 执行结果。
7. 返回文本回答和必要的结构化信息。
8. 展示工具调用状态和操作确认信息。
9. 处理超时、取消和异常响应。

## 2.3 输入

- 用户消息；
- 用户身份上下文；
- 会话 ID；
- 请求 ID；
- 必要的请求配置。

用户身份必须来自后端认证系统，不能由客户端任意指定后直接信任。

## 2.4 输出

- Agent 文本回答；
- 会话标识；
- 执行状态；
- 必要的来源引用；
- 操作确认请求；
- 安全、业务或系统错误信息。

## 2.5 核心组件

规划包括：

- Agent API；
- Request Schema；
- Conversation Handler；
- Agent Runtime Adapter；
- Response Schema。

具体 API 路由和 Schema 由 TASK-006 设计，前端交互由 TASK-013 实现。

## 2.6 与其他模块的关系

```text
Frontend
   │
   ▼
Agent API
   │
   ▼
Interaction Layer
   │
   ▼
Agent Runtime
   │
   ▼
Workflow & State
```

## 2.7 第一版范围

- 支持文本对话；
- 支持多轮会话；
- 支持用户身份上下文；
- 支持返回工具执行状态；
- 支持高风险操作确认交互；
- 支持返回 RAG 来源引用。

第一版是否支持流式响应尚未冻结，在 TASK-006 确认。

## 2.8 明确不做

- 复杂多模态交互；
- 语音实时对话；
- 视频理解；
- 多 Agent 群聊界面；
- 复杂消息协同平台。

# 3. Reasoning & Planning：推理与规划层

## 3.1 模块定位

Reasoning & Planning 负责理解用户意图，并决定 Agent 应该采取什么行动。

它是 Agent 决策过程的核心。

模型可以提出执行计划，但计划是否允许执行，必须经过后端安全和权限控制。

## 3.2 核心职责

1. 理解用户自然语言。
2. 识别用户意图。
3. 判断是否需要知识检索。
4. 判断是否需要业务工具。
5. 选择可用工具。
6. 生成工具参数。
7. 解释工具返回结果。
8. 判断是否需要继续执行。
9. 组织最终回答。

## 3.3 输入

- 用户当前消息；
- 对话上下文；
- 系统指令；
- 可用工具描述；
- RAG 检索结果；
- 上一步执行结果；
- 当前工作流状态。

## 3.4 输出

- 意图判断；
- 下一步执行动作；
- RAG 检索请求；
- Tool 调用请求；
- 最终回答；
- 拒绝或澄清请求。

## 3.5 典型决策场景

| 用户问题               | 预期路径                |
| ---------------------- | ----------------------- |
| 商品支持哪些功能？     | RAG 检索                |
| 退货规则是什么？       | RAG 检索                |
| 商品还剩多少库存？     | 库存 Tool               |
| 我的订单是什么状态？   | 订单查询 Tool           |
| 帮我取消订单           | 订单取消流程及必要确认  |
| 我的退款是否处理完成？ | 退款查询 Tool           |
| 这个商品有什么特点？   | RAG，必要时结合商品查询 |
| 商品库存是否足够下单？ | 实时库存 Tool           |

## 3.6 推理约束

模型不能：

- 自行决定用户身份；
- 自行提升权限；
- 直接访问数据库；
- 调用未注册工具；
- 绕过高风险操作确认；
- 将 RAG 文档中的指令当作系统指令；
- 将未执行的操作描述为已经成功。

## 3.7 核心组件

规划包括：

- LLM Adapter；
- Prompt Template；
- Intent Recognition；
- Tool Selection；
- Structured Output；
- Result Interpretation。

模型供应商和参数配置由 TASK-006 详细设计确定。

## 3.8 第一版范围

第一版采用受控的单 Agent 推理流程。

不建设复杂的自主规划平台。

# 4. Knowledge & Memory：知识与记忆层

## 4.1 模块定位

Knowledge & Memory 负责为 Agent 提供外部业务知识和必要的对话上下文。

该模块包含两个不同概念：

1. Knowledge：业务知识检索。
2. Memory：对话上下文和必要的运行状态。

二者不能混为一谈。

## 4.2 Knowledge：业务知识

业务知识主要通过 RAG 实现。

知识来源包括：

- 商品说明；
- 商品使用手册；
- 售后政策；
- 退换货规则；
- 配送规则；
- 常见问题；
- 业务操作说明。

RAG 负责从文档中检索相关内容，并将检索结果提供给 Agent。

### 4.2.1 知识处理流程

```text
文档上传
   │
   ▼
文档解析
   │
   ▼
文本提取
   │
   ▼
文本切分
   │
   ▼
Embedding
   │
   ▼
向量索引
   │
   ▼
检索
   │
   ▼
相关内容
   │
   ▼
Agent 上下文
```

### 4.2.2 知识检索约束

- 检索内容必须满足用户可见性权限。
- 检索结果属于不可信外部内容。
- 文档不能修改系统指令。
- 文档不能赋予 Agent 业务权限。
- 文档更新和删除后，旧版本不能继续被检索。
- 最终回答应尽可能提供来源引用。

## 4.3 Memory：对话上下文

Memory 负责保存 Agent 运行所需的必要上下文。

可能包括：

- 会话标识；
- 历史消息；
- 当前工作流状态；
- 待确认操作；
- 必要的短期上下文。

第一版不建设复杂的长期用户画像和自主记忆系统。

## 4.4 知识与实时业务数据的区别

| 信息类型     | 获取方式  |
| ------------ | --------- |
| 商品使用说明 | RAG       |
| 售后政策     | RAG       |
| 配送政策     | RAG       |
| 当前库存     | 库存 Tool |
| 当前订单状态 | 订单 Tool |
| 当前支付状态 | 支付 Tool |
| 当前退款状态 | 退款 Tool |

RAG 不能替代实时业务查询。

## 4.5 核心组件

规划包括：

- Knowledge Service；
- Document Parser；
- Chunking；
- Embedding；
- Vector Store；
- Retrieval；
- Reranker（属于 TASK-005 技术评估范围，第一版不强制引入）；
- Conversation Context；
- State Persistence。

## 4.6 对应 TASK

- TASK-005：RAG 知识库建设。
- TASK-006：Agent 对话上下文和工作流状态管理。

## 4.7 明确不做

- 自研 Embedding 模型；
- 自研向量数据库；
- 复杂长期记忆系统；
- 自动建立未经授权的用户画像；
- 将历史对话作为业务事实的唯一来源。

# 5. Tools & Execution：工具与执行层

## 5.1 模块定位

Tools & Execution 是 Agent 与电商业务系统之间的受控执行接口。

Agent 通过工具调用真实业务能力，但不能直接访问数据库。

## 5.2 强制调用链

```text
Agent
  │
  ▼
Tool Registry
  │
  ▼
Tool
  │
  ▼
Business Service
  │
  ▼
Repository
  │
  ▼
MySQL
```

这是整个项目必须遵守的核心架构约束。

## 5.3 Tool 核心职责

每个 Tool 需要定义：

- 工具名称；
- 工具描述；
- 参数 Schema；
- 调用权限；
- 对应 Service；
- 返回结构；
- 错误处理；
- 是否具有副作用；
- 是否需要确认；
- 幂等要求；
- 审计要求。

## 5.4 第一版候选工具

以下是候选工具范围，具体开放范围由 TASK-007 详细设计确认。

### 商品工具

| 工具                 | 用途          | 类型 |
| -------------------- | ------------- | ---- |
| `search_products`    | 搜索商品      | 只读 |
| `get_product_detail` | 获取商品详情  | 只读 |
| `get_sku_detail`     | 获取 SKU 信息 | 只读 |

### 库存工具

| 工具            | 用途     | 类型 |
| --------------- | -------- | ---- |
| `get_inventory` | 查询库存 | 只读 |

### 订单工具

| 工具             | 用途               | 类型   |
| ---------------- | ------------------ | ------ |
| `get_order`      | 查询订单           | 只读   |
| `list_my_orders` | 查询当前用户订单   | 只读   |
| `cancel_order`   | 取消允许取消的订单 | 写操作 |

### 售后工具

| 工具                             | 用途         | 类型     |
| -------------------------------- | ------------ | -------- |
| `get_after_sales_policy`         | 查询售后政策 | 知识查询 |
| `get_after_sales_application`    | 查询售后申请 | 只读     |
| `create_after_sales_application` | 创建售后申请 | 写操作   |

候选清单不代表全部工具必须在第一版开放。

## 5.5 Tool 参数校验

所有 Tool 输入必须通过明确的 Schema 校验。

例如：

```json
{
  "order_no": "示例订单号"
}
```

不能因为模型生成了一个参数，就直接信任其内容。

需要校验：

- 类型；
- 长度；
- 格式；
- 必填字段；
- 枚举值；
- 参数之间的关系；
- 当前用户是否有权操作目标资源。

## 5.6 身份上下文

用户身份由后端认证系统提供。

不允许使用模型生成的：

- `user_id`；
- `is_admin`；
- `role`；
- `permission`；

作为最终权限判断依据。

Tool 必须将可信的执行上下文传递给 Service。

## 5.7 Tool 与 Service 的关系

Tool 不得重复实现业务规则。

例如订单取消：

```text
cancel_order Tool
       │
       ▼
OrderService.cancel_order()
       │
       ▼
检查用户权限
       │
       ▼
检查订单状态
       │
       ▼
执行取消业务
       │
       ▼
Repository
       │
       ▼
MySQL
```

订单能否取消，最终由 Order Service 决定。

## 5.8 Tool 返回值

Tool 返回结构化数据。

需要区分：

- 成功；
- 业务拒绝；
- 权限不足；
- 参数错误；
- 资源不存在；
- 状态冲突；
- 外部服务异常；
- 系统异常。

模型只能根据真实执行结果组织回复，不能自行编造操作成功。

## 5.9 对应 TASK

- TASK-006：工具注册和 Agent 工具调用机制。
- TASK-007：电商业务工具及 Service 集成。

# 6. Workflow & State：工作流与状态层

## 6.1 模块定位

Workflow & State 负责管理 Agent 的执行过程和运行状态。

LangGraph 是第一版 Agent 工作流的核心技术。

## 6.2 工作流基本流程

```text
START
  │
  ▼
接收用户请求
  │
  ▼
上下文加载
  │
  ▼
安全检查
  │
  ▼
意图理解与路由
  │
  ├──────────────┐
  │              │
  ▼              ▼
知识检索       Tool 调用
  │              │
  ▼              ▼
检索结果处理   工具结果处理
  │              │
  └──────┬───────┘
         │
         ▼
     结果验证
         │
         ▼
     最终回答
         │
         ▼
        END
```

这是逻辑流程示意，不是已经冻结的 LangGraph 节点定义。

## 6.3 主要职责

1. 管理 Agent 节点执行顺序。
2. 根据条件决定下一节点。
3. 管理运行状态。
4. 保存必要的上下文。
5. 控制执行循环。
6. 处理超时和异常。
7. 支持高风险操作暂停等待确认。
8. 支持恢复或终止运行。

## 6.4 State 的概念

Agent State 是一次 Agent 运行过程中需要共享的数据集合。

可能包括：

- conversation_id；
- request_id；
- 当前用户上下文；
- 当前消息；
- 历史消息；
- 意图识别结果；
- RAG 检索结果；
- Tool 调用请求；
- Tool 执行结果；
- 操作确认状态；
- 最终回答；
- 错误信息；
- 运行元数据。

以上为逻辑字段示意，不是最终 State Schema。

具体字段和序列化方式由 TASK-006 设计确定。

## 6.5 状态持久化

需要区分：

- 会话历史；
- Agent 工作流状态；
- 待确认操作凭据；
- 业务执行记录。

这些数据的生命周期和安全要求不同。

具体采用 MySQL、Redis 或其他方式保存，需要在 TASK-006、TASK-007 详细设计中确认。

- Tool 调用超时；
- 重试次数；
- 单次请求预算。

具体数值由 TASK-006 设计并通过测试验证。

# 7. Guardrails / Security & Permissions：安全与权限层

## 7.1 模块定位

该模块贯穿 Agent 的整个执行过程。

负责防止用户输入、外部文档、模型输出和工具调用导致越权、数据泄露或不安全操作。

安全控制不能只依赖 Prompt。

## 7.2 信任边界

系统需要区分可信和不可信内容。

| 内容                 | 信任级别       |
| -------------------- | -------------- |
| 后端认证结果         | 可信           |
| 后端授权结果         | 可信           |
| Service 业务校验结果 | 可信           |
| 系统 Prompt 模板     | 受控可信       |
| 用户输入             | 不可信         |
| RAG 文档             | 不可信         |
| LLM 输出             | 不可信         |
| 外部 API 返回内容    | 不可信         |
| Tool 参数            | 必须校验       |
| Tool 执行结果        | 需要结构化验证 |

模型不能通过文本声明改变自身权限。

## 7.3 Prompt Injection 防护

需要考虑：

- 直接注入；
- 间接注入；
- 恶意知识库文档；
- 伪造系统消息；
- 伪造工具结果；
- 多轮诱导；
- 中文、英文和混合语言攻击；
- Base64、Hex、URL 等编码内容；
- Unicode 和零宽字符；
- 诱导模型泄露敏感信息；
- 诱导模型调用未授权工具。

防护方式包括：

1. 明确信任边界；
2. 将用户输入和外部文档作为不可信内容处理；
3. 使用受控 Prompt 模板；
4. 对工具执行实行白名单；
5. 对工具参数实施 Schema 校验；
6. 使用后端身份和权限上下文；
7. 对高风险操作进行确认；
8. 对关键输出进行验证；
9. 对安全事件进行记录；
10. 通过攻击样本开展安全评测。

不能只依赖关键词黑名单或 System Prompt。

## 7.4 工具权限控制

工具执行前必须检查：

- 工具是否已注册；
- 当前用户是否允许调用；
- 参数是否合法；
- 目标资源是否属于当前用户或允许访问范围；
- 当前业务状态是否允许操作；
- 是否需要用户确认。

最终权限判断必须在 Service 层完成。

## 7.5 高风险操作确认

高风险操作采用：

```text
Prepare
   │
   ▼
展示操作摘要
   │
   ▼
用户明确确认
   │
   ▼
Confirm
   │
   ▼
验证确认凭据
   │
   ▼
后端二次校验
   │
   ▼
Service 执行业务
```

确认凭据应绑定：

- 用户；
- 会话；
- 操作类型；
- 目标资源；
- 关键参数摘要；
- nonce；
- 过期时间；
- 消费状态。

必须防止：

- 参数被篡改；
- 凭据过期；
- 重复使用；
- 并发重复消费；
- 跨用户使用；
- 跨会话使用。

一次性消费需要具备原子性，并结合业务幂等。

## 7.6 敏感信息保护

以下信息不能暴露给模型或前端：

- LLM API Key；
- 数据库密码；
- JWT Secret；
- 支付宝私钥；
- 支付凭据；
- 用户密码；
- Refresh Token；
- 不必要的个人敏感数据。

日志和 Trace 需要脱敏。

## 7.7 RAG 安全

- 检索前执行权限过滤；
- 检索内容不能覆盖系统指令；
- 文档不能授予业务权限；
- 文档更新后旧版本不能继续检索；
- 文档删除后旧索引不能继续检索；
- 来源引用必须可追溯。

## 7.8 安全设计基线

详细安全要求以 `docs/architecture.md` 为准。

该文件当前 Review 和冻结状态以项目实际记录为准。

## 7.9 对应 TASK

- TASK-005：RAG 文档安全和检索权限。
- TASK-006：Agent 执行安全和运行约束。
- TASK-007：业务 Tool 权限和高风险操作确认。
- TASK-015：安全测试和最终验证。

# 8. Verification：验证层

## 8.1 模块定位

Verification 负责检查 Agent 执行过程中的关键结果，防止 Agent 根据不可靠信息输出错误结论或声称操作成功。

## 8.2 核心职责

1. 验证工具调用结果结构。
2. 验证业务操作结果。
3. 检查必要字段。
4. 检查结果状态。
5. 检查来源引用。
6. 识别工具执行失败。
7. 防止模型编造业务结果。
8. 对关键业务结果进行确定性断言。

## 8.3 验证对象

| 对象           | 验证内容                   |
| -------------- | -------------------------- |
| 用户输入       | 格式、长度和必要约束       |
| Tool 参数      | Schema、参数范围和业务关联 |
| Tool 结果      | 返回结构和执行状态         |
| 业务写操作     | Service 实际执行结果       |
| RAG 结果       | 来源、权限和版本           |
| Agent 最终回答 | 是否与真实结果一致         |

## 8.4 业务结果验证

对于订单取消、售后申请等操作：

不能只根据模型说“操作成功”就返回成功。

应当以 Tool 和 Service 的实际执行结果为依据。

例如：

```text
用户请求取消订单
       │
       ▼
调用取消订单 Tool
       │
       ▼
OrderService 执行
       │
       ▼
返回真实业务结果
       │
       ▼
Verification 检查结果
       │
       ▼
Agent 组织回复
```

## 8.5 验证失败处理

验证失败时：

- 不得声称业务成功；
- 必要时终止当前工作流；
- 返回可理解的错误信息；
- 保留必要的诊断记录；
- 对可能产生副作用的操作进行状态核查。

## 8.6 对应 TASK

- TASK-006：工作流结果验证。
- TASK-007：工具和业务操作结果验证。
- TASK-015：自动化测试和确定性验收。

# 10. Agent Evaluation：Agent 评测层

## 10.1 模块定位

Agent Evaluation 负责评估 Agent 是否能够正确、安全、稳定地完成目标任务。

不能只用“回答看起来不错”作为验收标准。

## 10.2 评测维度

### 意图理解

评估：

- 用户意图识别是否正确；
- 是否正确区分知识查询和业务查询；
- 是否正确识别需要澄清的请求。

### RAG 效果

评估：

- 检索召回质量；
- 检索相关性；
- 来源引用正确性；
- 无答案场景是否正确处理；
- 权限过滤是否有效。

### Tool Calling

评估：

- 工具选择是否正确；
- 参数是否正确；
- 工具调用是否符合权限；
- 是否正确处理工具失败；
- 是否避免不必要的工具调用。

### 业务正确性

评估：

- 订单查询是否返回正确用户数据；
- 库存查询是否读取实时数据；
- 订单取消是否遵守业务规则；
- 售后申请是否遵守售后规则；
- 高风险操作是否经过确认；
- 是否存在重复执行。

### 安全性

评估：

- Prompt Injection 防护；
- 跨用户数据访问；
- 工具越权；
- RAG 权限绕过；
- 敏感信息泄露；
- 确认凭据重放；
- 并发重复执行。

### 稳定性

评估：

- 超时处理；
- 模型调用失败；
- 工具执行失败；
- 工作流异常；
- 重试行为；
- 错误恢复。

## 10.3 评测数据集

需要建立具有代表性的测试样本。

类别包括：

- 普通商品问答；
- 商品详情查询；
- 售后规则问答；
- 库存查询；
- 订单查询；
- 订单取消；
- 售后申请；
- 不完整请求；
- 无权限请求；
- Prompt Injection；
- 跨用户攻击；
- 恶意 RAG 文档；
- 工具执行异常；
- 模型调用异常。

测试数据应覆盖正常、边界、异常和攻击场景。

## 10.4 评测方式

结合：

- 确定性自动化断言；
- Tool 调用记录检查；
- RAG 检索指标；
- 人工抽样评估；
- 安全测试；
- E2E 测试。

不能只依赖 LLM-as-a-Judge 判断业务操作是否正确。

涉及订单、退款、权限和安全的场景必须有确定性断言。

## 10.5 对应 TASK

TASK-015：系统级测试与最终评测。

# 11. Performance & Cost Management：性能与成本管理层

## 11.1 模块定位

Performance & Cost Management 负责控制 Agent 的执行时间、资源消耗和模型调用成本。

## 11.2 主要指标

需要关注：

- 单次请求总耗时；
- LLM 调用次数；
- LLM 调用耗时；
- 输入 Token；
- 输出 Token；
- RAG 检索耗时；
- Tool 执行耗时；
- 工作流节点数量；
- 单次请求成本；
- 错误率；
- 超时率。

## 11.3 执行限制

第一版应设置：

- LLM 请求超时；
- Tool 请求超时；
- 最大工作流步骤；
- 最大 Tool 调用次数；
- 最大重试次数；
- 最大上下文长度；
- 单次运行预算。

具体限制值由 TASK-006 根据实际模型和工具运行情况确定。

## 11.4 成本控制

可以采用：

- 避免不必要的模型调用；
- 控制上下文长度；
- 对重复知识检索进行合理缓存；
- 根据任务选择合适模型；
- 限制工具调用循环；
- 记录 Token 使用量；
- 设置异常成本保护。

不能为了降低成本而跳过权限校验、业务校验或必要的安全检查。

## 11.5 性能降级

当外部模型服务不可用时：

- 不应影响普通电商业务 API；
- 不应将模型调用失败伪装成业务成功；
- 应返回明确错误；
- 对可恢复错误实施有限重试；
- 对不可恢复错误及时终止工作流。

RAG 服务不可用时，Agent 可以在能力允许的情况下明确告知用户知识检索暂不可用，不得编造检索结果。

# 16. 架构验收标准

AI Agent 总体设计应满足以下要求。

## 16.1 模块完整性

- 十大模块职责明确；
- 模块之间的输入输出关系清晰；
- 不存在职责严重重叠；
- 不将逻辑模块误认为独立微服务。

## 16.2 业务边界

- Agent 不直接访问数据库；
- Tool 不直接操作 Repository；
- Tool 必须调用 Service；
- Service 负责业务规则和权限；
- RAG 不替代实时业务查询。

## 16.3 安全边界

- 用户身份来自后端；
- 模型不能提升权限；
- Tool 必须白名单管理；
- 参数必须经过 Schema 校验；
- 高风险操作必须确认；
- 确认凭据必须防重放；
- 并发操作必须安全；
- 敏感信息不能泄露；
- RAG 内容不能覆盖系统指令。

## 16.4 运行能力

- 工作流状态可管理；
- 执行过程可追踪；
- 异常能够处理；
- 运行限制明确；
- 关键结果可验证；
- Agent 效果可评测；
- 模型成本可统计。

## 16.5 项目范围

- 不新增顶层 TASK；
- 不扩大为多 Agent 平台；
- 不引入微服务和 Kubernetes；
- 不引入不必要的复杂基础设施；
- 不提前冻结尚未确认的技术选型。

# 17. 设计变更原则

本设计中的以下内容属于 V1.2 Agent 架构基线：

1. 第一版使用单 Agent 工作流。
2. 使用 LangGraph 管理 Agent 工作流。
3. RAG 与实时业务查询分离。
4. Tool 是 Agent 与业务系统之间的受控接口。
5. Tool 必须复用现有业务 Service。
6. Service 是业务规则和权限的最终执行边界。
7. 高风险操作采用 Prepare / Confirm。
8. 安全控制不能只依赖 Prompt。
9. Agent 运行过程必须可追踪和可评测。
10. 不建设复杂多 Agent 自主协作平台。

如需调整，应说明调整原因、技术影响、业务风险、实现成本和对已完成 TASK 的影响，并由项目负责人确认。
